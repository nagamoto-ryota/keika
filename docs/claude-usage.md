# Claude の使い方の記録

作品を作る過程で、Claude Code とアプリの中の Claude をどこでどう使ったかを、理由と試行錯誤つきで日ごとに残します。

## 1日目（2026-11-02）

- **Claude Code が本線**: 設計書と計画をリポの外に置き、Claude Code が失敗する試験から順に書いています。
- **最初のコミットを架空データだけにした**: キックオフ前に作った入力データと、期間中に書いたコードを履歴で区別するためです。
- **読み取りの形を固定した**: Claude が読んだ結果を、日付・署名の有無・サービスと頻度などの決まった項目（`DocFacts`）で保存します。あとの機械の点検はこの保存結果に対して走るので、文章を送り直さずに済みます。
- **試行錯誤: 受け取りの形を作り直した**: `DocFacts` をそのまま Claude の出力の形にすると、公式の上限（省略可の項目は合計24、null を許す項目は合計16）を超えると公式文書で分かりました。全項目を必須にした受け取り用の形（`WireFacts`）を別に作り、「無い」は空文字で受けて保存前に直す形に変えました。
- **断られた時の備え**: 介護の記録には病名や服薬が出てくるので、安全機能に誤って断られる可能性を考え、`fallbacks: "default"` を有効にし、断られた書類は「分からない」として扱います。
- **キーの扱い**: 作品専用のキーを `.env` からだけ読みます（環境変数は `.env` が無い時だけ）。別の認証に黙って流れて、他の組織に課金されるのを防ぐためです。
- **実物の読み取りが初回で通った**: U04 の14件を読み、56秒・API 14回・約 $0.75 でした。1件あたり約 $0.05 なので、126件を全部読み直しても約 $7 です。測定を何回か回しても予算内に収まる見込みです。
- **実物で見つかったこと**: 利用票の週の回数を、曜日から数える時と数えない時で揺れていました。曜日が書かれていれば数えるよう手順に足しました。
- **Claude の点検が初回で動いた**: 1体の Claude に手順（`skills/`）と4つの道具（書類を読む、台帳を引く、指摘を報告する、候補を取り下げる）を持たせました。1人あたり45〜70秒、約 $0.30 です。全121件の読み取りは298秒・約 $5.50 でした。
- **直した点**: 最初の指摘は文が長く、根拠も6件並びました。忙しいケアマネが読めるよう、100字くらい・根拠は3件までにしました。
- **まだの課題**: 書き足し案に、記録に無い行動（「訪問し」など）が混ざることがあります。〇〇の空欄で残すよう調整します。
- **作り手のケアマネの感想で変えた所（1日目）**: 根拠は押すと原文が開く形にし、ファイル名と長い日付を画面から外しました。「対応した」ボタンは廃止し、記録に対応が出たら Claude が根拠つきで指摘を閉じる形にしました。根拠を確かめられない時は閉じず、前回の指摘を黙って消さずに残します。
- **「楽になってる？」という問い**: 点検だけでは宿題が増えるだけ、と作り手のケアマネの問いで整理しました。指摘の一覧より先に、工程の進捗を1枚で見せる画面を作ることにしました。
- **画面を3回作り直した**: 指摘のカード → 日付の表 → やること一覧。作り手のケアマネの「最後いつやったかじゃなくて、やるべきことやったか、やってないならそれはなにか」で、日付を読ませる画面をやめました。Claude には指摘ごとに「何をするか」の一行（`todo`）を出させています。
- **増える指摘の修正**: 前回の指摘を残す仕組みで、点検のたびに件数が増える問題が実物で出ました（対象の書き方が回ごとに違うため）。番号で出し直させる形に変えました。

- **独立レビューで見つかった実害を直した**: 別の Claude（Opus）にブランチ全体を読ませ、再現コードで確かめさせました。1本の DB 接続の共有で同時アクセスが落ちる、ストリームの途中の切断で口述が消える、1文字の引用で根拠の検査を抜けられる、「おばあちゃん」のような呼び方で別の人に保存される、日付の形が違うと点検が黙って消える、などです。再現の試験を先に書いて直しました（`tests/test_hardening.py`）。
- **採点も別の Claude に任せた**: 語の一致だけの機械の採点は言い換えを落とします。判定表を持つ係が意味で判定し、表に無い指摘は答えを見ない別の係が書類だけで判定します。作る本線はこの判定に関わりません。
- **架空の入口データで気づいた誤判定の直し**: 入口5件のうち4件が要確認に回りました。「2時」→14:00、「転んだ」→「転倒」を「話に無い語」と誤判定していたためで、言い換えの扱いを直して0件になりました。

## Claude Code の使い分け（何を選び、何を選ばなかったか）

**選んだ物**

- `CLAUDE.md`: 開発で実際に守っているルール（架空データのみ、医療の線引き、測定の扱い）。
- `.claude/hooks/commit_guard.py`（コミットの前の hook）: API キー、会話ログ、`.env`、`data/`、000- 以外の電話番号、試験の失敗を止めます。作る過程で試験が落ちたままコミットしたことが3回あったので、試験も見ます。文書だけのコミットでは回しません。一時コピーで本物の Claude Code を動かし、キーを入れたコミットが止まることを確かめました。
- `.claude/agents/boundary-reviewer.md`: 医療の線引きと事実の捏造だけを見る独立レビュアー。結論を渡さず、再現できた物だけを報告させます。

**選ばなかった物**

- Python を編集するたびに試験を回す hook: 全試験に2分かかり、編集のたびに待たされます。事故はコミットの時に起きていたので、コミットの時だけ見ます。

**独立レビュアーを回して分かった事**

過去の指摘の実物（重複を除いて113件）に線を越えた物はありませんでしたが、止める検査の方に抜けがありました。守っていたのは機械の検査ではなく、プロンプトでした。試験（`tests/test_boundary_review.py`）を先に書いて、次を直しました。

- 薬名を主語にした中止や減量の助言、「かもしれません」型の病名の推測が検査を通っていた。
- 整文で薬の量が変わる（1錠→2錠、半錠、5ミリグラム→5グラム）、「飲めていない」が「飲めている」になる、話に無い病名や受診や「至急」が入っても、自動で保存されていた。
- 話していない居宅訪問、日時が、本文以外の欄からそのまま記録になっていた。
- 人名の修正欄を通すと、薬名や数字の検査を消せた。話に無い呼び方でも別の人の記録になった。
- 薬名の候補に、確かめずに残した語や、薬でない語（デイサービスなど）が出た。

機械で止められない物も残っています。話に無い事実一般（「独居で歩行器を使用」など）は語の一覧では見つけられず、プロンプトと人の確認に頼ります。指摘の文の事実と引用が合っているかも、引用が原文にあるかまでしか確かめていません。書き足し案は画面に「実際に行った事だけを残してください」と出すにとどめ、自動で記録には入れません。

## アプリのモデルの使い分け（測定の途中）

架空データ122通の読み取りと、話9件の整文を、3つのモデルで比べました（`eval/compare_models.py`）。

| モデル | 読み取りの費用 | 読み取りの時間 | Opus と書類の種類が違う | 整文の費用 | 整文で人に回った数 |
|---|---|---|---|---|---|
| Opus 5.5 | $6.03 | 285秒 | （基準） | $0.42 | 1 |
| Sonnet 5.5 | $2.72 | 164秒 | 0通 | $0.17 | 4 |
| Haiku 5.5 | $0.22 | 307秒 | 36通 | $0.02 | 1 |

- **Haiku は選びません。** 書類の種類の取り違えが36通あり、人名を薬名として確認に出しました（「満つ橋」など）。話を直さず人に回さないまま保存した物もあり、安いですが任せられません。
- **整文は Opus のままにします。** Sonnet は読み間違えた人名の直し（`name_fixes`）を書かず、人に回る数が1件から4件に増えました。1回の費用の差は数セントで、人の手間の方が高くつきます。
- **読み取りは Opus のままにします。** 同じコードで読み取りだけを変えて1回ずつ測り、どちらがどちらか伏せて別の Claude に採点させました（`20261103-064516-read-sonnet-2`、`20261103-064927-read-opus-2`）。

| 読み取り | 穴（厳しい側〜甘い側） | わなの誤り | 表に無い指摘の誤り | 読み取りの費用 |
|---|---|---|---|---|
| Sonnet 5.5 | 17〜19 / 21 | 0 / 5 | 2 | $2.72 |
| Opus 5.5 | 17〜18 / 21 | 0 / 5 | 2 | $6.03 |

  穴の数に差は出ませんでした。ただ、Sonnet は計画書の期間を第2表の援助期間で読み、まだ先の期限を「あと57日」と知らせました。読み取りの差額は書類122通で一度きりの約 $3.3 で、人を誤った期限で動かす方が高くつきます。確認用データも Opus の読み取りで測っているので、提出前には替えません。Sonnet は環境変数 `KEIKA_MODEL_READ` で選べます。比較は各1回です（ばらつきは下の節）。上限で止まった回（`20261102-223216-read-sonnet`）は比較に使いません。

- **比べて見つかった不具合:** Sonnet の方が穴を1つ多く当てたように見えましたが、モデルの差ではありませんでした。Opus は虐待防止委員会の題名に「新任職員研修の予定」まで読み取り、点検のプログラムがそれを研修の実施と数えて、研修切れの指摘を消していました。詳しく読んだ方が損をする不具合です。委員会の題名では数えないように直しました。

## 薬と医療の線の再確認（本物の Claude）

検査を直した後の `eval/run_boundary.py` は、話5件すべてで薬名を話のとおりに残し、線を越えた文は0件でした（`boundary-20261103-064803`、$0.68）。「レボドバ」は書類の「レボドパ」と並べて見せ、勝手に直しません。

検査が強すぎる所も見えました。本人の「薬をやめたい」という話を引いた指摘が3件、薬の中止の助言と同じ形として落ち、その話を人に知らせる指摘が残りませんでした。そこで、本人の願い（やめたい、減らしたい、増やしたい、飲みたくない）は、根拠の引用に同じ語がある時だけ助言と見なさないようにしました。隣に助言があれば止まり、引用に無ければ止まり、整文で話に無い願いが足されても止まります。直した後の再確認（`boundary-20261103-072053`、$0.57）は、落ちた指摘0件、線を越えた文0件で、指摘の中に「胸の痛み・服薬をやめたいとの訴え」が残り、主治医への情報提供を検討済みか確かめる形になりました。

## 音声入力の決め方

ブラウザの音声認識は標準で音声を外部へ送ります（MDN の説明）。そこで OS の音声入力を主な入口にし、「話す」ボタンは端末内の認識（`processLocally`）が日本語で使える時だけ出すようにしました。使えない時に黙って外部送信へ切り替える処理は外しました。

- Claude デスクトップアプリの内蔵ブラウザ（Chrome 152 相当）で試すと、日本語も英語も `unavailable` で、ボタンは出ません。手元の Windows の Chrome ではボタンが出て、話した内容が入りました。ページが毎回調べるので、環境ごとにコードを変える必要はありません。
- 手元で話すと、単語の間に空白が入り、句読点は付きませんでした。この空白で、話した「1 錠」を話に無い分量と見なす誤りと、「飲め て は い ない」を見落とす誤りが起きると分かったので、空白を外してから検査します（`join_spoken`）。通常の空白だけを外す最初の直しでは、話し終わりの確定結果に空白が残ったため、空白の種類を問わず外すようにし、ブラウザが古い JS を使い続けないようにしました。
- OS の音声入力なら外部へ送らない、とは言えません。Windows の Win + H はオンラインの音声認識を使うと Microsoft が説明しています。
- ケイカは PC の中で動くので、スマホからは開けません。スマホの案内は入れていません。

## 同じ条件で回した時のばらつき

読み取りからやり直して2回（`20261103-094248-var-1`、`20261103-095120-var-2`）回し、読み取りを流用した回（`20261103-064927-read-opus-2`）と並べました。どの回か伏せて、別の Claude が判定表と意味で照らしました。

| 回 | 指摘の穴（厳しい基準） | 指摘の穴（甘い基準） | 先回り（区分まで一致） | わなの誤り | 費用 | 時間 |
|---|---|---|---|---|---|---|
| var-1 | 19/21 | 20/21 | 2/2 | 0/5 | $8.63 | 504秒 |
| var-2 | 17/21 | 18/21 | 2/2 | 0/5 | $8.57 | 498秒 |
| read-opus-2（委員会の不具合を直す前の点検） | 18/21 | 18/21 | 2/2 | 0/5 | $2.27（点検のみ） | 185秒 |

- 穴の数は3回で 17〜19（厳しい基準）動きます。1回の数字をそのまま性能と読まない方がよいです。
- 出たり出なかったりした物が2件（算定理由の空欄、福祉用具の継続の検討）。Claude に任せた点検の揺れです。3回とも外れた物は1件で、測定を重ねても出ません。
- 研修切れは3回とも厳しい基準で外れました。機械の案内が「年1回以上行って記録する」だけで、切れている事実を書いていませんでした。最後の実施日と1年を超えた事を出すように直しました（測定の後の修正で、この表の数字には入っていません）。
- 表に無い指摘で、誤りと判定された物は3回とも0件でした。ただ、この採点は原本と照らしていません。「確かめられない」とした物のうち会議の要点の2件は、次の節で原本と照らして誤りと分かりました。
- 回数は3回だけで、作り手側が作った架空データでの結果です。実地の精度ではありません。

## 話した内容を入れた後の測定

入口の5素材を取り込んでから1回測りました（`20261103-101332-inbox-3`、$2.87）。読み取りは保存結果を流用し、別の Claude が原本とも照らして採点しました。

- 指摘の穴 19/21（厳しい基準、外れは算定理由の空欄と、8/19 の記録の中身）、先回り 2/2、わなの誤り 0/5。研修切れの案内の修正はこの回に入っています。
- 表に無い指摘9件は、正当4、誤り4、グレー1でした。誤りは多めです。
- 話5件のうち4件は記録になり、利用者、種別とも正しく、話に無い事実や薬名の直しはありませんでした。2人の話が入った1件は2件に分かれました。

**見つかって直した物（採点の後の修正で、上の数字には入っていません）**

- 話に「飲み忘れなし」があると、話した時刻まで「話に無い」と扱い、記録にせず人に回していた。時刻の欄に本文の検査を通していたのが原因です。人に回ったので話は失われていませんが、記録が無いため「今月の訪問はまだ」という誤った先回りも出ていました（誤り4件の1件）。
- 人の呼び方（「能登さん」）が薬名の確認に出ていた。
- 他の書類に担当者会議の記載があるのに「要点が見当たりません」と言っていた。記載があれば、足りるか確認する案内にしました。

**残っている物**

- 会議の要点の1件は、計画書に記載があるのに読み取りで拾えておらず、「見当たりません」のままです。
- 同意書の範囲の指摘1件（誤り）は Claude の読み違いで、直していません。
- 話の中の関係者の名前（介護ソフトの CSV と字が違う物など）は、利用者の名前と違って直らないことがあります。
- 1回だけの測定で、作り手側が作った架空データでの結果です。実地の精度ではありません。

## MCP の受け口

**既定で止めています。** 別の AI から呼べる道具は、呼ぶ側の判断で思わぬ話が流れ込みます。架空データの実演専用とし、データベースと同じフォルダの `mcp_on` が無ければ、Claude にもデータベースにも触らずに断ります。説明文からも、呼ばれやすくする言い回しを外しました。

Claude Desktop から話した内容を記録する `record_text` を1つだけ作りました（`src/keika/mcp_server.py`）。

- **新しい処理を足しません。** 入口のファイルと同じ `process_text` を通します。別の入口を作ると、薬名や医療の線の検査を通らない抜け道になるためです。保存した記録には `intake:mcp` と残り、未確認の下書きになります。
- **結果は実際の処理から返します。** 保存した時と、人の確認に回した時で文を分けます。ここで「記録しました」と言って記録が無い、という事を避けるためです。
- **読み出しの道具は作りません。** 記録や書類を Claude Desktop から読めるようにすると、利用者の情報の出口が増えます。今回は入れる方向だけにしました。
- **スマホからは使えません。** ケイカは PC の中で動くので、PC の Claude Desktop だけが対象です。
